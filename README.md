# Hosanna Studio Backend

Production REST API for Hosanna Studio: songs, folders, worship services,
musician QR-token access, and studio (JWT) admin auth. Backed by
PostgreSQL via Prisma. See **API_DOCUMENTATION.md** for the full endpoint
reference.

This project is API-only — no frontend assets are served. The studio is
a separate project that talks to this server over HTTP.

## Stack

Node.js, TypeScript, Express, Prisma ORM, PostgreSQL, Zod, Better Auth,
`@hosanna/chordpro`, Model Context Protocol (`@modelcontextprotocol/server`).

## MCP server

Hosanna exposes an MCP interface for AI clients (songs, services, ChordPro):

- **HTTP:** `POST /mcp` (Streamable HTTP). Optional `Authorization: Bearer <Better Auth session>` with an active organization for song/service tools. ChordPro tools work without auth.
- **stdio:** `HOSANNA_BEARER_TOKEN=<token> npm run mcp`

Resources live under `hosanna://…` (guide, schemas, skills). Task prompts include `songs.*` and `services.*`. Workflow skills are in `docs/mcp/skills/` and also served as MCP resources.

## Running with Docker (recommended)

```bash
cp .env.example .env
# edit .env: set real JWT secrets and admin password
docker compose --env-file .env up --build
```

This starts Postgres + the API on `http://localhost:3000`. The container's
entrypoint runs `prisma migrate deploy` automatically before booting.

Seed the bootstrap admin + demo data once the stack is up:

```bash
docker compose exec api npx prisma db seed
```

## Running locally (without Docker)

```bash
npm install
cp .env.example .env   # set DATABASE_URL to point at your local Postgres
npx prisma generate
npx prisma migrate deploy
npm run prisma:seed
npm run dev             # tsx watch, http://localhost:3000
```

## Note on the committed migration

`prisma/migrations/20260725000000_init/migration.sql` was written by hand
against `schema.prisma` rather than generated by `prisma migrate dev`,
because this sandbox's network policy blocks `binaries.prisma.sh` (the CDN
Prisma's CLI downloads its query-engine binary from), so `prisma generate`
/ `prisma migrate dev` could not be executed here to auto-generate it.

**Before your first real deploy**, run once in an environment with normal
internet access:

```bash
npx prisma migrate dev --name init
```

This will validate the schema against a live Postgres and let Prisma
regenerate the migration if anything doesn't match (it should match exactly,
but Prisma-generated migrations are the canonical source of truth going
forward). Alternatively, just run `npx prisma migrate deploy` against the
committed migration — it's plain SQL and will apply as-is.

## Environment variables

See `.env.example` for the full list. At minimum, set:

- `DATABASE_URL`
- `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` (e.g. `openssl rand -hex 64`)
- `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` before running the seed script

For live note pings and **song annotation sync**, also set `FCM_PROJECT_ID`,
`FCM_CLIENT_EMAIL`, and `FCM_PRIVATE_KEY`, enable Firestore, and deploy
`firestore.rules` (see
[docs/ANNOTATIONS_FIREBASE.md](docs/ANNOTATIONS_FIREBASE.md)). Firebase Storage
is not required.

## Scripts

- `npm run dev` — watch mode (tsx)
- `npm run build` / `npm start` — compile to `dist/` and run
- `npm run prisma:migrate:dev` — create/apply a migration in development
- `npm run prisma:migrate` — apply pending migrations (production)
- `npm run prisma:seed` — bootstrap admin + demo content
